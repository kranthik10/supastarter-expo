# ADR-014 — Analytics taxonomy, consent, and provider boundaries

- **Status:** Accepted and implemented in Phase 3.6
- **Date:** 2026-09-02
- **Context:** The repository had a small analytics stub and an earlier draft that mixed dotted and lower-snake event names, identified users with raw email/name, and did not define provider/client/server or consent boundaries. Phase 3 needs reusable product analytics without leaking credentials, invitation tokens, signed URLs, or user-entered PII.
- **Decision:** Use a client-safe `@repo/analytics` facade with a central typed catalog using `lower_snake_case` product events. Use a separate `@repo/analytics/server` subpath for selected server-authoritative events. Use a fetch-based PostHog provider rather than a React Native or Node SDK so the client/server boundaries remain explicit and the dependency surface stays small. Missing configuration selects a no-op provider; tests use a fake provider.
- **Identity:** The authenticated internal Better Auth user ID is the analytics distinct ID. Identify traits are limited to safe product metadata (`locale`, `theme`, safe plan/context, app variant, and app version). Raw email, full name, phone, address, authentication/session data, and provider credentials are not sent. Logout and user changes reset provider identity.
- **Consent:** `user_preferences.analytics_enabled` is a new additive preference distinct from `marketing_opt_in`. The mobile app loads the server-authoritative value before identifying/capturing an authenticated user. Disabled analytics makes capture, identify, group, and screen no-ops and resets provider identity. If consent cannot be loaded, analytics remains disabled.
- **Organization context:** Expose provider-independent `group('organization', organizationId)` for the active organization. Organization switching updates the group and emits only a safe `organization_switched` event. No organization secrets or billing-provider identifiers are sent.
- **Screen privacy:** Track logical screen names at the Expo Router root boundary. Dynamic invitation tokens, signed URLs, query strings, and bearer-like path values are reduced to safe route categories such as `invite`.
- **Server ownership:** The API emits `organization_created` and `invitation_accepted` only after successful business operations. Client code does not duplicate those logical events. Server provider failures are swallowed and cannot roll back product mutations.
- **Validation:** Event names and per-event property keys are runtime-checked in addition to TypeScript types. Forbidden keys are normalized case-insensitively; unknown, nested, unsupported, or dangerous properties reject the event before provider invocation. This is a lightweight guardrail, not a complete legal/privacy review.
- **Dashboard extension (Phase 3.8):** The Home dashboard may emit only typed product events (`dashboard_viewed` and `dashboard_quick_action_selected`) through this facade. It must not send overview payloads, notification content, organization names, member emails, file metadata, or raw errors.
- **Alternatives rejected:** A new `analytics_events` table was rejected because it duplicates external analytics storage without a demonstrated product requirement. Reusing `marketing_opt_in` was rejected because marketing communication consent and product analytics consent have different semantics. A vendor SDK in screens was rejected because it would scatter provider coupling and risk native/server imports.
- **Consequences:** Product events are consistent and swappable; external ingestion remains optional; users can opt out; client bundles contain only intentionally public PostHog configuration; real PostHog ingestion remains an environment-dependent verification item. Phase 3.7 Monitoring/Sentry is not part of this decision.
