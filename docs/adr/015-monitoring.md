# ADR-015 — Monitoring boundaries and PII guardrails

- **Status:** Accepted and implemented in Phase 3.7
- **Date:** 2026-09-02
- **Context:** Phase 0 selected Sentry, but the repository had no monitoring package, SDK integration, error boundary, global unhandled-error handler, or server error boundary. Existing analytics privacy rules prohibit raw email/name and sensitive identifiers, and the storage/notification milestones introduced signed URLs, invitation tokens, and push tokens that must not enter diagnostic payloads.
- **Decision:** Add a small `@repo/monitoring` package with explicit client-safe root/policy exports, `@repo/monitoring/client` for React/client runtime integration, and `@repo/monitoring/server` for Hono/server integration. Use a fetch-based Sentry Store API provider with no-op fallback instead of adding native/Node SDKs to the shared graph. The client may use public `EXPO_PUBLIC_SENTRY_DSN`; the server uses private `SENTRY_DSN_SERVER`. Missing DSNs select no-op providers.
- **Sanitization:** Recursively redact normalized forbidden keys: password, token variants, session, authorization, cookie, secret, API/database URL, signed upload/download/presigned URL, invitation/password-reset token, push token, request/response body, payment/card/CVV, email, name, phone, and address. Redact bearer tokens, signed query values, JWT-like values, and tokenized invitation/reset paths in error strings/stacks. Context is bounded to safe scalar/nested diagnostics; request bodies and headers are never passed.
- **Expected errors:** Validation, authentication, authorization, not-found, conflict, precondition/quota, rate-limit, and known provider-not-configured outcomes are not captured. Unexpected uncaught errors, database/provider failures, invariant breaches, render failures, and unhandled client runtime/promise failures are captured. Hono `onError` is the primary uncaught server capture boundary to avoid duplicate procedure/middleware captures.
- **Identity/context:** User context is the Better Auth internal user ID only. Organization context uses opaque `organization_id` with optional bounded role/plan tier. Route context is sanitized through the Phase 3.6 logical route strategy; invitation-token routes reduce to `invite`, and server routes retain only safe procedure/path templates. Context is replaced on organization switch and cleared on logout/user change.
- **Client boundary:** A single root monitoring instance is initialized with release `${appSlug}@${appVersion}`, bounded environment, and platform. The root installs guarded web/JS-runtime unhandled handlers and wraps the existing navigation/query tree in `MonitoringErrorBoundary`; fallback UI exposes no stack or raw error.
- **Server boundary:** Hono’s `onError` captures only safe method, sanitized path, status, optional procedure/code, and bounded request ID. It returns the existing HTTP exception response or a generic 500 response without returning diagnostics.
- **Deferred:** Native crash capture, Sentry source-map upload, session replay, and performance tracing are deferred. Expo export verifies JavaScript compatibility only; it does not prove native crash capture, symbolication, or external Sentry ingestion.
- **Alternatives rejected:** A new monitoring/error database table was rejected because it duplicates Sentry storage. A generic logging framework was rejected because this milestone is error observability, not log aggregation. Session replay was rejected for the auth/billing/team/storage/notification privacy surface. Automatic SDK network breadcrumbs were not enabled because signed URLs/headers require explicit scrutiny.
- **Consequences:** Monitoring is swappable, privacy-safe by default, and non-fatal to product operations. Real Sentry delivery remains environment-dependent. Phase 3.8 Dashboard and later alerting/operations work are not part of this decision.
