# ADR-007 — Notification Architecture

- **Status:** Accepted — implemented in Phase 3.5
- **Date:** 2026-08-31
- **Context:** Push is first-class on mobile and must handle app states, token rotation, invalid providers, user preferences, in-app history, and safe deep links without exposing provider credentials.
- **Decision:** Use `expo-notifications` on the client with Expo Push Service as the V1 delivery path to APNs/FCM. The server owns `devices`, `push_tokens`, and `notifications`; protected tRPC procedures derive the recipient from the Better Auth session. `push_tokens.invalidated_at` records rotation, logout, and provider-invalid tokens. Notification rows are persisted before external push I/O, so in-app history does not depend on provider success.
- **Preference correction:** The implemented normalized `user_preferences` table is authoritative. It contains `invite_emails`, `billing_alerts`, and paired `quiet_hours_start/end`; the earlier draft reference to `users.notificationPreferences` JSONB is not used. `billing_alerts` gates billing push only and never deletes in-app history. Quiet-hours enforcement is deferred until a validated user timezone exists.
- **Provider boundary:** `@repo/notifications` is client-safe and exposes permission/token helpers and shared policy types. `@repo/notifications/server` is server-only and exposes `ExpoPushProvider`, `FakeNotificationProvider`, `NotConfiguredNotificationProvider`, and the notification creation/delivery seam. `EXPO_ACCESS_TOKEN` and any future provider credentials are read only by the server provider path and never enter the mobile bundle.
- **Registration:** User intent triggers `requestPermissions()`, then `getExpoPushTokenAsync({ projectId })` on a physical iOS/Android device. The app persists an opaque installation identifier locally and calls `notifications.registerPushToken`; registration is transactional and idempotent for the authenticated user/install/token association. The schema does not claim a permanent hardware identifier.
- **Categories and data:** V1 uses finite categories `team`, `billing`, `security`, and `system`. Push/in-app data is constrained to safe routing context `{ route?: string; orgId?: string }` with an allowlist. Invitation bearer tokens, password-reset tokens, sessions, presigned URLs, credentials, and PII-rich payloads are forbidden.
- **Read model:** Protected `notifications.list` uses bounded cursor pagination; `getUnreadCount`, `markRead`, and `markAllRead` always scope by `ctx.user.id`. Nullable `organization_id` is descriptive context with `ON DELETE SET NULL`, never an authorization grant.
- **Delivery semantics:** Provider acceptance means the Expo service accepted a ticket, not that a device displayed the notification. Immediate `DeviceNotRegistered` ticket errors invalidate tokens. Receipt reconciliation and scheduled workers are deferred.
- **Alternatives:** Firebase-only, OneSignal, unrestricted client-created pushes, and storing provider credentials on mobile were rejected. A full email/SMS/campaign platform is outside this milestone.
- **Consequences:** Real physical-device push requires an EAS/native build and APNs/FCM configuration, so it remains deferred. Fake and not-configured providers allow deterministic local verification without fabricated external delivery results.
